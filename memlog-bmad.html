Le memlog de BMad

Le fichier .memlog.md est la mémoire de travail d'une skill : une liste de lignes qu'on ne fait qu'allonger. Les documents livrés, comme spec-<slug>.md, sont réécrits à partir de lui. Cette page explique le fichier, le script, et la façon dont un LLM en tire la spec.

01

Rôle : la source de vérité, pas le livrable

Le script memlog.py ne sait qu'écrire : créer le fichier, ajouter une ligne, changer un champ d'en-tête. Il ne produit jamais la spec. C'est l'agent qui exécute la skill qui lit le memlog et réécrit les documents.

Le memlog garde tout ce qui a compté, dans l'ordre. Les documents livrés sont recalculés à partir de lui à chaque exécution. Plusieurs skills peuvent donc alimenter le même espace dans n'importe quel ordre sans conflit de fusion.

02

Format du fichier

Un en-tête de simples lignes clé: valeur, puis une liste plate. Pas de sections : l'ordre chronologique tient lieu de structure. Extrait réel de ton memlog de spec.

1---
2topic: CLI qui importe dans Azure DevOps des arbres de work items…
3updated: 2026-10-07T12:14
4---
5
7- (note) Création. Entrées : idée forgée forge-ado-yaml-importer.md…
8- (decision) La spec l'emporte sur les recommandations R1, R3, R4, R5…
9- (capability) CAP-1 describe : génère à la racine du repo la config…
45- (direction) L'utilisateur conteste la condition 'sans parent'…
47- (event) Spec re-dérivée : hypothèse 'racine sans parent' retirée…
En-têteChamps libres posés par init --field ou set. updated est ajouté automatiquement et toujours placé en dernier.
Fin d'en-têteLa première ligne qui vaut exactement ---. Un --- au milieu d'une valeur ne coupe donc pas l'en-tête.
Entrée- (type by auteur) texte sur une seule ligne. Le type et l'auteur sont facultatifs.
ComptageLe script compte les lignes qui commencent par - .
03

Les trois commandes

Chaque commande vise le fichier de la même façon : --workspace DIR (le fichier est DIR/.memlog.md) ou --path FILE. L'une des deux est obligatoire, jamais les deux.

CommandeParamètresEffetÉchoue si
init--field clé=valeur, répétableCrée le dossier si besoin et le fichier avec son en-tête. Ajoute updated.Le fichier existe déjà (code 2) ; un --field sans = (code 2).
append--text obligatoire ; --type, --by facultatifsAjoute une ligne en fin de fichier. Retours à la ligne et espaces multiples sont réduits à un espace. Ne touche pas à updated.Fichier absent ou en-tête mal formé. Rien n'est écrit dans ce cas.
set--key, --value obligatoiresRemplace ou ajoute un champ d'en-tête, puis met updated à jour.Fichier absent ou en-tête mal formé.

Chaque commande affiche une ligne JSON, pour que l'agent connaisse l'état sans relire le fichier :

{"ok": true, "memlog": "…/spec-ado-yaml-importer/.memlog.md", "entries": 94}
04

Les trois règles de conception

Elles sont écrites dans la docstring de memlog.py et le code n'offre rien qui permette de les contourner.

+

Ajout seul, dans l'ordre

Aucune commande pour modifier, supprimer ou insérer plus haut. Une décision plus récente remplace l'ancienne en s'ajoutant après elle ; l'historique reste intact.

→

Écriture à l'aveugle

Chaque commande écrit sans contexte et renvoie l'état en JSON. L'agent ne relit le fichier qu'à la reprise, et il le lit lui-même, pas par le script.

∅

Pas de statut

Aucun champ « terminé ». Fin de travail, blocage ou pause s'enregistrent comme une entrée : append --type event --text "spine finalized".

05

Écriture sûre et ajouts en parallèle

Plusieurs subagents peuvent ajouter des lignes au même moment. Le script s'assure que le système d'exploitation place chaque écriture à la fin du fichier, sans étape intermédiaire où un autre processus pourrait s'intercaler.

06

Une exécution de bmad-spec

D'après skills/bmad-spec/SKILL.md. La lecture du memlog n'a lieu qu'au départ ; tout le reste n'est qu'écriture.

07

Du memlog à la spec : la dérivation

Aucun code ne traduit le memlog. Le LLM le fait en suivant le prompt de la skill : SKILL.md (157 lignes) et le gabarit assets/spec-template.md (49 lignes). Aucune phrase ne dit « telle ligne va dans telle section » : la correspondance vient des noms et du jugement du modèle.

Les memlogs des autres skills

Chaque skill a son propre memlog dans son dossier de travail, et son propre vocabulaire de types : le script n'en impose aucun. Le document livré par chaque skill est tiré de son memlog, comme la spec.

bmad-architecture va plus loin : elle préfère lire un memlog plutôt que la source dont il vient, et elle peut écrire dans le memlog d'une spec pour que bmad-spec en tienne compte à sa prochaine exécution.

10

Pièges et bonnes pratiques

À éviter

Modifier la spec à la main

La modification n'est pas dans le memlog : elle est écrasée à la prochaine réécriture. Passe par bmad-spec (« update the spec ») pour qu'elle devienne une entrée.

À éviter

Éditer le memlog

Corriger ou supprimer une ligne casse l'historique sur lequel repose la règle « la dernière l'emporte ». Ajoute une nouvelle entrée qui remplace l'ancienne.

À savoir

Le memlog peut être en avance

Une autre skill peut ajouter des lignes au memlog de la spec. La spec n'est réécrite qu'à la prochaine exécution de bmad-spec.

À savoir

La réécriture n'est pas déterministe

Deux réécritures du même memlog peuvent différer dans la formulation. Les CAP-N restent stables parce qu'ils sont écrits dans le memlog et que la Spec Law interdit de les renuméroter.

À savoir

updated trompe

append ne met pas ce champ à jour. Il date le dernier init ou set, pas la dernière entrée.

Pour aller plus loin

Rendre la traduction plus stricte

Ajoute une règle de correspondance dans persistent_facts ou un gabarit à toi dans _bmad/custom/bmad-spec.toml. bmad-customize peut l'écrire.

# wi-bmad/_bmad/custom/bmad-spec.toml
[workflow]
persistent_facts = [
  "Mapping memlog → spec : (capability) → Capabilities ; (constraint) → Constraints ; (assumption) → Assumptions ; (question) non résolue → Open Questions ; (decision) de périmètre → Non-goals ; (decision) de format ou de code de retour → cli-contract.md.",
]
# spec_template = "{project-root}/_bmad/custom/spec-template.md"

Aide-mémoire

# créer (échoue si le fichier existe)
uv run _bmad/scripts/memlog.py init   --workspace <dossier> --field topic="…" --field goal="…"

# ajouter une entrée (une seule ligne, type et auteur facultatifs)
uv run _bmad/scripts/memlog.py append --workspace <dossier> --type decision --text "…"
uv run _bmad/scripts/memlog.py append --workspace <dossier> --type idea --by user --text "…"   # → - (idea by user) …

# changer un champ d'en-tête (met updated à jour)
uv run _bmad/scripts/memlog.py set    --workspace <dossier> --key goal --value "…"

# viser le fichier directement au lieu du dossier
uv run _bmad/scripts/memlog.py append --path <dossier>/.memlog.md --text "…"

# chaque commande répond
{"ok": true, "memlog": "<chemin>/.memlog.md", "entries": <n>}
Ce que le script ne fait pasPourquoi
Lire, chercher, filtrerL'agent lit le fichier lui-même, seulement à la reprise.
Modifier ou supprimer une entréeAjout seul, par conception.
Imposer une liste de typesChaque skill choisit son vocabulaire.
Produire la spec ou un autre documentC'est le travail de l'agent, guidé par le prompt de la skill.
Gérer un statutUn état est un événement : --type event.
